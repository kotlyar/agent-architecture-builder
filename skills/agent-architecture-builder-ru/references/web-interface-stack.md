# Бесплатная основа панели управления

Применяй этот документ только после того, как критерии из
`control-interface-and-storage.md` подтвердили необходимость панели в браузере.
Все выбранные по умолчанию библиотеки должны быть бесплатными, иметь открытый
исходный код и не требовать платной облачной службы.

## 1. Основной набор

<!-- parity:web.default-stack -->

Для рабочей панели управления по умолчанию используй:

- React и TypeScript — устройство пользовательского приложения;
- Vite — сборка и местный запуск разработки;
- Tailwind CSS — оформление;
- shadcn/ui — доступные для изменения компоненты интерфейса.

При реализации используй актуальные стабильные версии. Закрепи версии в файле
зависимостей и проверь текущие лицензии прямых зависимостей. Используй только
бесплатную основу Tailwind CSS и не добавляй платный набор только потому, что он
связан с выбранной библиотекой.

Основной набор подходит, когда нужны связанные экраны, точное управление
состояниями, разграничение прав, подтверждения действий и развитие приложения во
времени.

## 2. Дополнительные библиотеки только по потребности

<!-- parity:web.optional-libraries -->

- TanStack Table — когда обязательны отбор, сортировка, разбиение на страницы,
  выбор строк или работа со сложными таблицами. Не добавляй ради простой таблицы
  из нескольких строк.
- Recharts — когда пользователю действительно нужно сравнивать показатели или
  видеть изменение во времени. Не заменяй графиком число, которое понятнее
  показать текстом.

Перед добавлением любой библиотеки проверь её текущую лицензию, поддержку и
совместимость с уже выбранными версиями. Зафиксируй точные версии в файле
зависимостей и сохрани сведения о лицензиях.

## 3. Упрощённый вариант

<!-- parity:web.prototype -->

Streamlit допустим для первого внутреннего прототипа, если одновременно выполнены
условия:

- система предназначена для одного человека или небольшой внутренней группы;
- основная логика уже написана на Python;
- нужны простые формы, таблицы, показатели и запуск действий;
- не требуется сложное разграничение прав;
- не требуется богатая работа с очередями и связанными состояниями в реальном
  времени;
- прототип не выдаётся за окончательную архитектуру без проверки на реальной
  работе.

Не выбирай Streamlit только ради более быстрого начала, если уже известны
требования к сложной панели: последующая замена может оказаться дороже прямой
реализации на основном наборе.

## Правило стоимости

<!-- parity:web.cost -->

Первая версия должна запускаться локально без платной библиотеки компонентов и
обязательной коммерческой облачной службы. Размещение, управление личностями,
аналитика и управляемая база данных являются отдельными решениями; оцени их
стоимость до включения в архитектуру.

## 4. Какие экраны создавать

<!-- parity:web.required-views -->

Создавай только экраны, подтверждённые рабочими случаями пользователя:

| Потребность | Возможный экран |
|---|---|
| Увидеть общую картину | Обзор текущих задач, состояний и отклонений |
| Поставить и изменить работу | Задачи и запуски |
| Проверить опасное действие | Подтверждения с точной версией и последствиями |
| Управлять самостоятельными исполнителями | Агенты и их состояние |
| Управлять периодической работой | Расписания |
| Проверить результат | Материалы, основания и измерения |
| Разобрать сбой | Журнал событий и ошибок |
| Настроить доступ | Пользователи, роли и разрешения |

Не создавай все экраны заранее. Для первой версии выбери кратчайший путь от
постановки задачи до проверенного результата.

## Обязательные состояния внешнего действия

<!-- parity:web.required-states -->

Если система может менять внешнюю среду, интерфейс должен различать:

1. черновик;
2. ожидает подтверждения;
3. подтверждено для точных параметров;
4. выполняется;
5. успешно завершено;
6. завершено с ошибкой;
7. результат неизвестен;
8. отменено или срок подтверждения истёк.

Перед подтверждением показывай точную цель, учётную запись, действие, материал
или изменение, бюджет или предел и последующую проверку. Изменение подтверждённой
версии отменяет прежнее подтверждение.

## 5. Обязательные требования к панели

<!-- parity:web.safety -->

- Интерфейс показывает фактическое состояние из источника истины, а не хранит
  собственную несогласованную копию.
- Опасное действие показывает цель, учётную запись, точное изменение, версию,
  стоимость и последствия до подтверждения.
- После подтверждения изменение содержимого требует нового подтверждения.
- Неизвестный результат внешнего действия сначала проверяется; кнопка не должна
  молча повторять действие.
- Пользователь может отличить черновик, ожидающее подтверждение, выполняемую,
  завершённую, отменённую и ошибочную работу.
- У каждой ошибки есть понятное сообщение и безопасный следующий шаг.
- Основные действия доступны с клавиатуры, поля имеют подписи, а состояния не
  различаются только цветом.
- Панель работает на узком экране, если интервью подтвердило работу с телефона.
- Секреты и ключи доступа не передаются в код браузера и не записываются в
  журналы.
- Проверяются права на сервере; скрытая кнопка не считается защитой.

## 6. Граница между панелью и сервером

<!-- parity:web.boundary -->

Панель отвечает за показ, ввод и намерение пользователя. Сервер отвечает за:

- проверку личности и прав;
- правила переходов между состояниями;
- хранение источника истины;
- защиту от повторного внешнего действия;
- выполнение инструментов;
- журнал событий и подтверждений.

Панель может временно сохранять данные для показа, но должна явно обозначать
устаревшее состояние. Очередь, подтверждения и фактические результаты остаются
на сервере или в выбранном источнике истины.

Не помещай деловые правила только в браузер. Разговорный интерфейс, панель и API
должны обращаться к одним серверным правилам, чтобы разные способы управления не
давали разные полномочия.

## Когда панель пока не нужна

<!-- parity:web.do-not-build -->

Не создавай панель в первой версии, если:

- единственному подтверждённому пользователю удобен разговор или командная
  строка;
- первая полезная версия ещё проверяет сам рабочий процесс;
- у состояния задач нет устойчивой схемы;
- границы подтверждений остаются неизвестными;
- нет оснований считать, что общий обзор заметно сократит труд или риск.

В этом случае включи в комплект спецификацию интерфейса и условие пересмотра, но
оставь первую реализацию проще.

## 7. Проверка готовности

<!-- parity:web.readiness -->

Перед завершением убедись, что:

- каждый экран связан с подтверждённой потребностью из интервью;
- выбран более простой набор, если он покрывает потребность;
- нет обязательной платной зависимости;
- записаны лицензии и точные версии;
- есть проверка сборки и ключевых пользовательских путей;
- подтверждение, отмена, ошибка, неизвестный результат и восстановление проверены
  отдельно;
- способ хранения соответствует `control-interface-and-storage.md`.
